# AGENTS.md

Instructions for coding agents that work on DiPlay.

## Vehicle scope

Production targets Android 9 / API 28, ECARX 753 / Qualcomm 820A, with the vehicle platform signature. Ship three packages: ARM64 (`arm64-v8a`, the default production package), ARMv7 (`armeabi-v7a`, the fallback) and x86_64 (test-only, for the emulator). Each release carries one APK per ABI, and the in-app updater downloads the package that matches the device's own ABI (an ARM64 unit checks ARM64). Other Android releases are debugging environments. App runtime, permission setup and recovery must not depend on ADB. Use [the permission checklist](docs/ADB_AND_PLATFORM_PERMISSIONS.zh-CN.md) and issue #21 as the implementation and validation reference. Vendor interfaces, firmware behavior and what has been verified on the car are recorded in [the platform notes](docs/ECARX_753_PLATFORM_NOTES.zh-CN.md); register a new interface, property id or broadcast there before using it.

## Checks

Match local validation to the actual change:

- Documentation, comments, credits and translation/string-only edits that do not change behavior, layout, resource keys/placeholders or build configuration need only `git diff --check` and a focused review of content, references, locale consistency and resource escaping. Do not launch full Gradle tests, lint, APK builds or native compilation for these changes; leave full validation to CI. Do not delay an explicitly requested commit or push while waiting for local full checks.
- For code, behavior or build changes, run relevant local checks. Run the full suite locally only when concrete integration risk requires it, when investigating a CI failure, or when the user requests it.
- If the user says to stop local checks or leave validation to CI, stop the checks and do not restart them unless asked. Report pending CI honestly; do not imply that uncompleted checks passed.

The full CI command from `.github/workflows/android.yml` is a reference, not a requirement for every delivery:

```sh
./gradlew :shared:testDebugUnitTest :common:testDebugUnitTest :home:testDebugUnitTest \
  :mobile:lintDebug :home:lintDebug :maphost:lintDebug :siribridge:lintDebug \
  :mobile:assembleDebug :home:assembleDebug :maphost:assembleDebug :siribridge:assembleDebug
```

Set `ANDROID_HOME` or `local.properties` if Gradle cannot find the SDK.

## Source ownership

The module layout and current ownership are described in [the architecture notes](docs/ARCHITECTURE.zh-CN.md). The Rust core migration was merged in PR #97; its old work branches and closed issue #96 are historical records, not instructions to continue a migration. Rust owns protocols, session state, media queues and scheduling, recovery, codec/route decisions, navigation state, vehicle-data conversion and input protocols. Kotlin remains the Android host and platform adapter: UI, lifecycle, permissions, focus requests, Bluetooth/hotspot, USB/VPN, storage and vehicle SDK calls. Platform adapters report events/capabilities and execute core requests; they do not keep a second copy of core state.

The ownership below describes production boundaries. Change one coherent owner and its callers/tests at a time; preserve Android 9 calibration, routing and recovery behavior, and update these rules when ownership changes. Reuse existing Rust media code. Before importing protocol code, compare the relevant [LIVI Rust crates](https://github.com/f-io/LIVI/tree/main/native/crates) and test vectors against our wire behavior; record the source revision, preserve required attribution, and check API 28 and all supported ABIs. Do not import its complete application/runtime merely to reuse a protocol module.

During development, run affected-module tests. Run the complete Checks command for a deliverable batch; do not repeat global checks for documentation-only changes. Track current acceptance and remaining work in [the acceptance matrix](docs/RUST_CORE_REMAINING.zh-CN.md), with links to supporting issues/PRs. Closed issues #96/#98/#99 preserve history; their closure does not establish every device/car acceptance item.

Keep shared-only internal-owner contracts in `shared/src/testCoreInternal/kotlin`, included by shared JVM/androidTest source sets only. General `testCore` references and `testCoreShadows` remain available to common/home tests; do not make production internal APIs public to compile fixtures in unrelated modules.

Migrated production core facades require native, including protocols, pairing, NTP, session state, media queues/clocks/DSP, navigation/HUD and vehicle conversion. Keep independent Kotlin test references and an explicit required-core load failure at startup. Bouncy Castle and Concentus are test-only; hardware/SDK capability fallbacks have separate platform requirements. Source implementation and necessary compilation do not establish combined device acceptance.

Rust sources live under `shared/src/main/rust/diplay-media/src/`: `protocols` (wire codecs/crypto/pairing/timing), `session` (lifecycle/recovery/deadlines/subscriptions), `media/audio` and `media/video` (media owners), `vehicle` (HID/vehicle/navigation/location), `platform` (JVM/NDK/shared stream lifetime), and `transport` (USBMUX/Lockdown/NCM). `lib.rs` only assembles these six namespaces. Keep an owner's private JNI module with that owner; do not add root compatibility re-exports, `#[path]` aliases, a catch-all utilities layer or split private state merely to relocate FFI. Preserve target-specific cfg, JNI/C ABI and existing public/private boundaries when moving code.

- `CarPlayHostActivity` owns the foreground session and window lifecycle. `CarPlaySidePanel` owns its panel views, gestures, animation callbacks and cleanup; the host supplies the current session geometry and actions. `CarPlaySafeAreaEditor` owns the safe-area switches, summary and editor overlay; the host supplies the activity size, palette and settings baseline. `CarPlayBackgroundSession` (its own file) hands the running session between hosts.
- `DiPlayActivity` owns page navigation and settings composition. `DiPlayControls` holds its custom text controls, and `DiPlayUpdates` owns update checks, downloads, verification and installation for that Activity lifetime. `DiPlayDiagnosticReport` builds the diagnostic report text from the application context.
- `CarPlayController` executes shared-service and wired teardown actions; its private `WirelessRun` retains one wireless generation's platform resources, callbacks and cleanup. Rust `session::{controller, wireless_state, wireless_recovery, watchdog}` own generations, lifecycle/handoff, retry budgets, deadlines and teardown decisions. Wi-Fi scan suppression stays with the controller across runs. `WirelessBluetoothConnection` selects and validates Bluetooth SDK targets and connects RFCOMM using the caller's cancellation predicate. `CarPlayStatus` holds the status contract. Its debug-log line for each status lives next to it (`debugLogMessage`), and `OrchestrationText` holds the text helpers shared across the package.
- `AndroidMediaSink` owns stream routing and renderer lifetimes. It updates native receiver destinations under the video ownership lock and disconnects old routes before retiring a stream. Rust receiver routes retain decoder references; video packets and mirror references stay in Rust until fed or dropped. `VideoDecoder`, `AudioRenderer` and `AudioFocusCoordinator` own decoding, playback and focus respectively. Keep codec worker ownership and release ordering with those implementations.
- Rust `media::audio::{buffered, buffered_state}` own buffered music TCP framing, decryption, queued and inaudible fed packets, RTP/NTP anchors, SETRATE/FLUSH, feed deadlines and bounded/paced intake. `media::audio::{queue, route}` own the retained receiver-to-renderer queue, RTP backlog recovery and arrival feedback; `clock_trim` owns music PI control and learned drift. Kotlin gates platform callbacks against pause/flush/close, commits a feed only for its current generation, and destroys/wakes the buffered owner before stopping its receiver. Renderer queue access is serialized against close; clocks stay on the output worker. AAC headers/configuration/access-unit slicing and PCM/Opus processing require Rust. Keep AudioTrack/AAudio, focus, route and head-unit calibration behavior.
- Rust `protocols::rtsp` owns control request framing and response encoding behind `RtspMessage`; its private `jni` constructs existing DTOs with bounded local references and UTF-16 strings. Keep the DTO constructor R8 rules, US_ASCII behavior, ProtocolException and receive limits. Rust `protocols::bplist` owns binary plist layout, types and decoding budgets behind `BplistCodec`; its private `jni` maps Java collections/scalars and delegates malformed UTF-16 replacement to the platform charset. Encoding has a shared native/fallback depth limit of 128; decoding retains its 32-level and work/payload limits. Rust `protocols::control_cipher` owns control/event framing, AEAD keys and independent wrapping counters. `ControlCipher` serializes operations and close; `AirPlaySession` closes both owners and rejects late installation. Close the event socket before waiting for its write lock. Keep the Decrypted DTO R8 constructor rule. Rust `iap2_body` owns CSM parameter framing and builder schema rules (type, unknown/repeated/required fields); `iap2_wire` owns scalars, list/terminator layout and typed field sizes. Kotlin retains immutable DTOs, descriptive schema metadata, its builder/reader API and platform UTF-8 conversion; schema errors carry input indexes so UTF-16 field names remain intact. `iap2_csm` owns bounded outer framing, resynchronization and link splitting; `iap2_link` owns synchronization, sequence/ACK/window state, retransmission, bounded queues and timers. These protocol facades require native; CSM/link serialize use with close and the link pump owns its engine with `use`. Old Kotlin algorithms are test-only.
- Rust `protocols::pair_verify` owns the complete M1/M2/M3/M4 handshake, ephemeral/shared/encryption keys, verification result and control keys. `PairVerify` serializes all handle use and close; `AirPlaySession` closes it after transport teardown. Kotlin supplies the live PairingStore lookup and platform UTF-8 conversion. Keep the lookup callback, PairingStore class name and ControlKeys constructor R8 rules. Preserve partial M1 commits, prior verified keys across new/failed handshakes, raw transcripts with first-32-byte crypto keys, and BC 1.79's canonical/low-order Ed25519 rejection boundary. Rust `protocols::pair_setup` owns the full SRP/M1–M6 exchange and proof/signature state. Kotlin retains platform PairingStore callbacks, identity storage and JCA hardware-key actions; Rust owns crypto primitives and MFi DER/raw conversion. Preserve save-before-sign ordering and close/reentry behavior. `num-bigint` modular exponentiation remains variable-time, matching the former BigInteger boundary; do not describe it as constant-time. BC is an independent test oracle, not a production provider.
- Rust `session::wireless_state` defines the opaque value token, queries and transitions for `WirelessRunState`; `session::wireless_recovery` owns run retry budgets, attempt validity/stage/timeout and failure decisions. Kotlin serializes tokens without decoding or duplicating active state. These are values, not heap handles. Kotlin extracts Java Throwable facts and assembles exceptions, and retains validation order, cancellable waits, watchdog scheduling and platform resource actions. Controller generations belong to Rust `session::controller`. Read validity under the attempt monitor, then call the external current predicate after releasing the getter lock.
- Rust `session::{controller, watchdog, airplay, iap2_handshake}` own controller/run/VPN generations and leases, lifecycle/teardown decisions, watchdog deadlines, RTSP negotiation/stream claims and identification/MFi/wired/wireless handshake actions, retries and counters. Kotlin serializes opaque GC value tokens and executes SDK/I/O/clock/cancellation/callback actions. Keep existing deadlines, wrapping, callback order, late-result disposal and SDK work outside core/resource locks. `transport::usbmux` owns framing, mux/TCP sequence/window/queues and send-success commits; `transport::lockdown` owns XML/plist framing and Pair/StartSession/StartService flows. Kotlin retains I/O, waits, exception references and PKIX identity/storage adapters. Simple SDK thread handoff mailboxes remain platform I/O adapters.
- Rust `protocols::{auth_setup, data_stream, iap_stream_queue}` own MFiSAP transcripts/crypto/OPACK, type130 framing/counters and the bounded tunnel queue. Platform certificate/signature/BAA callbacks preserve original Throwable identity; Kotlin retains socket actions and wait/notify. Close sockets before destroying their owners.
- Rust `media::video::{pacing, flow, selection}` own input/output timing, reference chains, decoder queues/backlog, byte conversion, codec configuration and degradation. Production video requires the Rust `vpipe` NDK loop (API 28+); initialization failure is explicit, with no Java playback loop. Kotlin retains configuration/Surface requests, capability enumeration, hardware availability probes and SDK resource guards, not duplicate policy state. Keep codec retries, software fallback and vendor parameter degradation. Host SDK pipe replay is test-only and distinct from real Android receiver/FD acceptance. Rust `media::video::codec_actions` is the commit boundary for actual codec-operation results, not planned rendering: only successfully shown output counts as rendered; a failed or oversized operation stops the rest of that batch's codec buffers (they stay with teardown) while every packet already transferred into the batch is still released; the Rust planners decide what to do and the NDK codec adapter commits what actually happened.
- Rust `protocols::timing` owns request/reply timing, peer correlation, sample selection and clock filtering; Kotlin owns sockets and clock reads. Preserve sample windows, signed/wrapping arithmetic and rounding calibration. Rust `media::video::{annexb, codec}` own screen timestamp/NAL/config layout; `ScreenStream` requires native framing/decryption and keeps platform sockets/callbacks. JNI startup failure releases its descriptor rather than selecting a Kotlin receiver.
- Rust `session::control_deadline` owns the wired Iap2ControlDeadline authentication window, unlimited mode, rounding and bounded polls. Kotlin passes clocks and executes existing wired I/O. Its opaque token has zero or two Long values, interpreted only by the selected core; no heap handle is allocated. Preserve Kotlin wrapping arithmetic, query snapshots before reentrant clock calls and the absence of clock reads after unlimited authentication. Wireless deadlines and watchdog scheduling are separate owners.
- Rust `media::audio::scheduler` owns output accounting, playback/prebuffer state, the granted-capacity start threshold, chunk limits, write-result actions, rebuffer and tail deadlines, buffer calibration and navigation-route decisions. Its facade stays on the renderer worker, allocated lazily, reset in place and closed by worker release. Kotlin executes clock reads and actual play/pause/write/focus/route actions, reporting successful actions back to the core. Renderer compressed packets always use Rust; old Kotlin queue/recovery algorithms are test-only. Rust `media::video::selection` chooses codecs and retry/probe plans; Kotlin reports codec facts, preserves platform Char folding, executes callbacks/create/sleep, and commits retry state after the retry callback. Hardware/SDK capability fallbacks remain platform behavior.
- Rust `media::audio::packetizer` owns the Java-socket microphone path's RTP/ChaCha counters, PCM wire conversion and capture/clock/MTU frame calibration. It reuses `uplink::seal`; Java DatagramSocket I/O remains when the SDK cannot share its FD. Counter getters/setters expose an opaque GC token, committed after successful sealing/array creation and before socket I/O. Preserve Int/Long wrapping, 48/24/16 kHz clock priority and 20/10/5 ms MTU calibration. MicrophoneConfig remains an immutable platform DTO; SDK capture/focus/effects and capture-start resource guards remain Kotlin. The old packetizer and Concentus are test-only references.
- Rust `vehicle::{vehicle_status, identification, vehicle_speed}` encode EV status, IdentificationInformation groups 20/21 and PASCD layout/checksum. Identification names use the existing platform string codec; PASCD numbers use the existing platform Formatter, including rounding, signed zero and non-finite spelling. Kotlin retains SDK queries, capability gates and subscriptions. PASCD production speed is fed by `EcarxVehicleSpeedSource` from ECARX `ISensor` 1048832 (m/s) and VHAL `GEAR_SELECTION`; real-car subscription paths have been observed; dynamic PASCD output and actual service-disconnect recovery remain unverified (see `docs/benchmarks/vehicle-speed-2026-11-14.md`).
- Rust `session::report_subscription` owns location/EV reporting subscriptions and deadlines; `vehicle::location` owns NMEA conversion. Location commits its one-second attempt before provider/send; EV commits its thirty-second deadline after successful send. Kotlin retains Calendar/Formatter and provider/transport actions, including their original failure ordering.
- Rust `session::playback` owns incremental iAP2 NowPlaying field parsing/retention and navigation renderer leases, quiet-tail expiry and aggregate route/priority decisions. Kotlin retains immutable publication DTOs, UTF-8 replacement/trim, clocks and renderer token objects. Opaque GC values require no native close lifetime; malformed fields preserve old values and a closed renderer cannot publish late playback.
- Rust `session::playback` also owns artwork track identity, recovery generations and the one-send-attempt budget, queue versions/content deduplication/cache eviction, and MediaCenter acquisition/publication decisions. Kotlin retains Handler/executor work, image references and recycling, MediaSession publication, Binder registration/calls/cleanup and uncertain-result guards. Preserve retry callback reentrancy, stale-session disposal and published-image lifetime. Commit publication only after a completed platform call for the still-current, non-uncertain session; a normal rejected publication still commits its attempted snapshot. The Kotlin facade consumes artwork queue snapshots as named results; business code no longer reads the variable-length native layout.
- Rust `media::audio::{uplink, scheduler}` own microphone read-error/no-audio recovery budgets and navigation-prompt duck/audible/release decisions, including the existing release delays. Kotlin retains AudioRecord restart/sleep/cancellation, AudioFocusRequest identity and actual grant results, pending Runnable identity and clocks. Read-error restart counts commit only after success; no-audio counts consume each attempt. Keep AudioFocusCoordinator resource entries, focus callback guards and applied-volume accounting with the platform objects.
- Rust `session::network_address` owns hotspot address selection/alternate ordering, scoped IPv6 readiness/filtering, bounded preferred-family waits and the evidence gate for persisting a family flip; Bonjour endpoint selection has its distinct IPv4/link-local/global/fallback order in this same owner. Kotlin supplies InetAddress capability facts and retains interface scans, cancellation, waits, logs and preference storage. Ordinary hotspot selection still accepts unscoped link-local IPv6; preferred-family recovery requires scoped link-local before ending its wait.
- Rust `session::hotspot_recovery` owns stable-sample confirmation, first-sample fast confirmation with change fallback, hotspot readiness deadlines/polls, radio-return wait budgets and process-wide radio outage expiry. Kotlin retains Android AP/interface identification and identity comparisons, clock/cancellation reads and SDK polling. Preserve callback/clock order, the 2/3-sample thresholds and 250/500 ms polls.
- Rust `session::p2p_startup` owns remembered-frequency validation, aligned/band/manual channel plans, bounded BUSY retry and compatibility fallback decisions. Kotlin retains WifiP2pManager operations, platform prerequisites/interlocks and original exception identities; uncertain timeouts cannot trigger another create request.
- Rust `vehicle::route_guidance::lane_update` owns complete 0x5204 lane parsing through the shared Rust iAP2 body parser. Kotlin only assembles immutable lane DTOs. Preserve first outer/inner scalar fields, all known duplicate-field widths, stable lane-index sorting, wire angle order, ±1000 unknown-angle omission and empty-body-only clear semantics.
- Rust `protocols::airplay` owns AirPlay capability/info declarations, fixed event/command bodies, VideoInCar control messages, Bonjour TXT/connect-probe wire values and bounded TCP probe retry plans. Kotlin supplies immutable configuration, platform text conversions and SDK/session actions; Android NSD FAILURE_ALREADY_ACTIVE resolution retries remain SDK-operation adapters. No second protocol encoder remains in production.
- Rust `media::audio::{routing, echo}` own audioType/channel/content/legacy-route and speaker-fallback decisions, far-end PCM/downmix/clock state and capture-clock alignment. Kotlin retains AudioTrack/AudioRecord/AEC capability facts, SDK actions and reference lifetimes; independent old DSP algorithms are test-only. A live microphone resolves the current output's echo reference at each software-AEC frame boundary without taking sink locks, retains the new ring before releasing its old reference, and serializes reads/rebinding with capture release. Recovered renderers keep independent rings so a failed worker's late writes cannot pollute the replacement; same-rate recovery does not reopen AudioRecord or its platform effects, while an incompatible output rate attempts the existing platform-AEC fallback. Buffered anchor/feedback reply schema and NTP conversion stay with the Rust buffered owner through the bplist platform bridge.
- Rust `vehicle::route_guidance` owns navigation TLV parsing, maneuver cache, expiry, clearing and ETA state behind `RouteGuidanceState`. Its Glance and ECARX output owners are process singletons; temporary owners close their handles, serialized with queries. Kotlin supplies clocks and live-session state, and retains SDK providers, subscriptions, frame wrapping and platform outputs. Keep the maneuver DTO R8 constructor rules; The navigation facade requires native; the independent Kotlin algorithm is test-only.
- Rust `vehicle::hid` encodes reports/descriptors, `touch_slots` owns pointer-to-slot state, and `cluster_arrow`, `lane_icon`, `day_night` own pure OEM conversion tables. Kotlin retains Android input, display dimensions, HID UID/metadata and head-unit adapters. Serialize touch report/use/close at the facade; a late report on a closed owner returns no report and Session returns false. An unhighlighted lane may still derive its direction from the raw highlight angle when its angles are empty. Other vehicle conversions require actual production callers before adding new adapters.

Wired USB results belong to their diagnostic run. Reject and release stale Connected results, transfer a pipe exactly once to the mux factory, and order mux publication with close/run replacement under the existing resource monitor. Do not close resources or perform I/O under that monitor. A run's finally block terminates only its locally owned startup watchdog, never a replacement run's watchdog.

## Adding or moving a setting

The Settings screen is grouped by driver goal, not by implementation.
`SettingsCategory`, `SettingsSection` and `SettingsInformationArchitecture` in
`common/src/main/java/com/shihab/diplay/SettingsInformationArchitecture.kt` define the groups.
`SettingsLayoutPolicyTest` fails when a section has no category or has more than one.

### Choose the category

Ask which goal the driver has when they look for the setting. Use the first row that fits.

| Category | Put a setting here when it controls… | Examples |
| --- | --- | --- |
| Connection | how the iPhone connects and how DiPlay starts | connection setup, connect on open, start with the car, USB permissions, car hotspot automation, iPhone choice, Android permissions |
| Display | how CarPlay looks on the head-unit screen | day/night mode, picture, size, resolution, frame rate, dock, system bars, multi-window resolution |
| Audio | what the driver hears | media and navigation streams, music buffer |
| Navigation | location and turn-by-turn guidance | location to iPhone, head-unit HUD and cluster guidance |
| Vehicle | how CarPlay fits this car and its driver | driving side, wheel keys (Siri, joystick and map zoom), car button, gestures that conflict with the head unit |
| Diagnostics | troubleshooting evidence | diagnostic reports |
| Advanced | experimental, firmware-specific or risky behavior | dashboard map, split screen, screen rotation, side panel, HEVC video, audio focus, audio channel mapping, buffered music, vehicle data |
| Overview | nothing new | see "Overview" below |

A setting goes to Advanced when it is experimental, depends on specific firmware, or is an opt-in that can break sound, video or the connection on some head units.
A control that fixes a common problem and is safe at its default (for example the audio stream choice) stays in its category.
Exception: a gated control that only its own audience sees, and that completes an everyday goal, stays in that goal's category.
Example: auto car hotspot depends on vehicle permissions and appears only for car-hotspot users, so it is in Connection.

Mark an experimental setting or card with the title suffix ` (experimental)`, never `· experimental`, a dash, or an `Experimental …` prefix.
Each locale MUST use its existing form: `(تجريبي)`, `(experimental)`, `(sperimentale)`, `(экспериментально)`, `(експериментально)`, `（实验性）`, `（實驗性）`, `（実験的機能）`.

### Add the code

1. To extend an existing card, add the control inside the `filteredSection(...)` block of a card in the correct category.
2. For a new card, add a `SettingsSection` entry and map it to exactly one category in `SettingsInformationArchitecture.sectionsByCategory`.
3. Build the new card with `filteredSection(content, SettingsSection.X, …)` inside `allSettingsSections()`.
   A plain `section(...)` call there MUST NOT be used: it renders on every category page.
4. A setting MUST NOT appear in two categories.
   Overview quick settings are the only duplicates. They MUST use the same persistence as the full control. Overview SHOULD NOT have more than four quick settings.
   A header shortcut MAY duplicate a Display setting when it uses the same persistence.
5. If the change reconnects CarPlay or applies at the next connection, the description MUST say so.
   A setting that only takes effect at the next connection MUST call `markReconnectNeeded()` after it saves.
   This shows the "Reconnect now" bar. It MUST NOT drop a running session without the driver's consent.
   Reconnect at once (`reconnectIfRunning()`) only after a dialog button that says "Apply and reconnect", or when the description says that the change reconnects CarPlay.
6. Add each new string to `common/src/main/res/values/` and to every `values-xx` locale folder.
   New Settings copy SHOULD use the `settings_` prefix. `SettingsTranslationsTest` fails when a `settings_*` string has no translation.
7. A control that opens a choice uses `button()` with the text `"Title · Value"`.
   That form renders as a setting row with the value and a chevron, and Search indexes the title.
8. When you move a control between categories, update `AdaptiveSettingsUiTest.settingsLiveWhereDriversLookForThem`.

### Overview

Overview holds the connection status, links to the categories, quick settings, About and Language.
Do not add a new setting to Overview. Add it to its category. Then promote it to quick settings only if drivers change it often.

## Settings layout

Spacing, size and shape in the Settings screen MUST come from one place.

1. A gap between blocks MUST use a named dp constant, such as `SETTINGS_BLOCK_GAP_DP`.
   A new literal gap value MUST NOT be added.
2. A size MUST NOT be a pixel constant (`*_PX`). Use dp, and clamp to the available window width.
   Test menus and panels on the current head unit at 1920×1080 pixels.
3. Controls in one row MUST have the same height.
   Corner radius MUST follow the control height. A new button MUST NOT set its own radius.
4. Every `SettingsCategory` except Overview MUST have a link on Overview.
   `AdaptiveSettingsUiTest.overviewLinksToEveryOtherCategory` checks this.
5. A layout change MUST include a screenshot at the current head unit size: 1920×1080 pixels,
   landscape, normal font scale. Do not add other screen sizes, portrait, large-font or RTL
   screenshot variants. Keep protocol and instrument-display dimension tests for their own formats.

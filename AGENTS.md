# AGENTS.md

Instructions for coding agents that work on DiPlay.

## Vehicle scope

Production targets Android 9 / API 28, ECARX 753 / Qualcomm 820A, with the vehicle platform signature. Ship three packages: ARM64 (`arm64-v8a`, the default production package), ARMv7 (`armeabi-v7a`, the fallback) and x86_64 (test-only, for the emulator). Each release carries one APK per ABI, and the in-app updater downloads the package that matches the device's own ABI (an ARM64 unit checks ARM64). Other Android releases are debugging environments. App runtime, permission setup and recovery must not depend on ADB. Use [the permission checklist](docs/ADB_AND_PLATFORM_PERMISSIONS.zh-CN.md) and issue #21 as the implementation and validation reference. Vendor interfaces, firmware behavior and what has been verified on the car are recorded in [the platform notes](docs/ECARX_753_PLATFORM_NOTES.zh-CN.md); register a new interface, property id or broadcast there before using it.

## Checks

Match local validation to the actual change:

- Documentation, comments, credits and translation/string-only edits that do not change behavior, layout, resource keys/placeholders or build configuration need only `git diff --check` and a focused review of content, references, locale consistency and resource escaping. Do not launch full Gradle tests, lint, APK builds or native compilation for these changes; leave full validation to CI. Do not delay an explicitly requested commit or push while waiting for local full checks.
- For code, behavior or build changes, run relevant local checks. Run the full suite locally only when concrete integration risk requires it, when investigating a CI failure, or when the user requests it.
- If the user says to stop local checks or leave validation to CI, stop the checks and do not restart them unless asked. Report pending CI honestly; do not imply that uncompleted checks passed.

The full CI command from `.github/workflows/android.yml` is a reference, not a requirement for every delivery:

```sh
./gradlew :shared:testDebugUnitTest :common:testDebugUnitTest \
  :mobile:lintDebug :maphost:lintDebug \
  :mobile:assembleDebug :maphost:assembleDebug
```

Set `ANDROID_HOME` or `local.properties` if Gradle cannot find the SDK.

## Source ownership

The module layout and current ownership are described in [the architecture notes](docs/ARCHITECTURE.zh-CN.md). The Rust core migration was merged in PR #97; its old work branches and closed issue #96 are historical records, not instructions to continue a migration. Rust owns protocols, session state, media queues and scheduling, recovery, codec/route decisions, navigation state, vehicle-data conversion and input protocols. Kotlin remains the Android host and platform adapter: UI, lifecycle, permissions, focus requests, Bluetooth/hotspot, USB/VPN, storage and vehicle SDK calls. Platform adapters report events/capabilities and execute core requests; they do not keep a second copy of core state.

The ownership below describes production boundaries. Change one coherent owner and its callers/tests at a time; preserve Android 9 calibration, routing and recovery behavior, and update these rules when ownership changes. Reuse existing Rust media code. Before importing protocol code, compare the relevant [LIVI Rust crates](https://github.com/f-io/LIVI/tree/main/native/crates) and test vectors against our wire behavior; record the source revision, preserve required attribution, and check API 28 and all supported ABIs. Do not import its complete application/runtime merely to reuse a protocol module.

For behavior changes, run affected-module tests according to the Checks policy above. Track current acceptance and remaining work in [the acceptance matrix](docs/RUST_CORE_REMAINING.zh-CN.md), with links to supporting issues/PRs. Closed issues #96/#98/#99 preserve history; their closure does not establish every device/car acceptance item.

Keep shared-only internal-owner contracts in `shared/src/testCoreInternal/kotlin`, included by shared JVM/androidTest source sets only. General `testCore` references and `testCoreShadows` remain available to common tests; do not make production internal APIs public to compile fixtures in unrelated modules.

Migrated production core facades require native, including protocols, pairing, NTP, session state, media queues/clocks/DSP, navigation/HUD and vehicle conversion. Keep independent Kotlin test references and an explicit required-core load failure at startup. Bouncy Castle and Concentus are test-only; hardware/SDK capability fallbacks have separate platform requirements. Source implementation and necessary compilation do not establish combined device acceptance.

Rust sources live under `shared/src/main/rust/diplay-media/src/`: `protocols` (wire codecs/crypto/pairing/timing), `session` (lifecycle/recovery/deadlines/subscriptions), `media/audio` and `media/video` (media owners), `vehicle` (HID/vehicle/navigation/location), `platform` (JVM/NDK/shared stream lifetime), and `transport` (USBMUX/Lockdown/NCM). `lib.rs` only assembles these six namespaces. Keep an owner's private JNI module with that owner; do not add root compatibility re-exports, `#[path]` aliases, a catch-all utilities layer or split private state merely to relocate FFI. Preserve target-specific cfg, JNI/C ABI and existing public/private boundaries when moving code.

- `DiPlayActivity` owns page navigation and settings composition. `DiPlayControls` holds its custom text controls, and `DiPlayUpdates` owns update checks, downloads, verification and installation for that Activity lifetime. `DiPlayDiagnosticReport` builds the diagnostic report text from the application context.
- `CarPlayController` executes shared-service and wired teardown actions; its private `WirelessRun` retains one wireless generation's platform resources, callbacks and cleanup. Rust `session::{controller, wireless_state, wireless_recovery, watchdog}` own generations, lifecycle/handoff, retry budgets, deadlines and teardown decisions. Wi-Fi scan suppression stays with the controller across runs. `WirelessBluetoothConnection` selects and validates Bluetooth SDK targets and connects RFCOMM using the caller's cancellation predicate. `CarPlayStatus` holds the status contract. Its debug-log line for each status lives next to it (`debugLogMessage`), and `OrchestrationText` holds the text helpers shared across the package.
- `AndroidMediaSink` owns stream routing and renderer lifetimes. It updates native receiver destinations under the video ownership lock and disconnects old routes before retiring a stream. Rust receiver routes retain decoder references; video packets and mirror references stay in Rust until fed or dropped. `VideoDecoder`, `AudioRenderer` and `AudioFocusCoordinator` own decoding, playback and focus respectively. Keep codec worker ownership and release ordering with those implementations.
- Rust `media::audio::{buffered, buffered_state}` own buffered music TCP framing, decryption, queued and inaudible fed packets, RTP/NTP anchors, SETRATE/FLUSH, feed deadlines and bounded/paced intake. `media::audio::{queue, route}` own the retained receiver-to-renderer queue, RTP backlog recovery, arrival feedback and the ordinary-audio feedback anchor with its sampleTime calculation and single-stream reply entry; buffered keeps its own reply schema. Kotlin reads the clocks once at the existing points, commits the start-callback fact and sends the returned entry. Kotlin gates platform callbacks against pause/flush/close, commits a feed only for its current generation, and destroys/wakes the buffered owner before stopping its receiver. Renderer queue access is serialized against close; clocks stay on the output worker. AAC headers/configuration/access-unit slicing and PCM/Opus processing require Rust. The AAC owner supplies ADTS/ASC primitives; `media::audio::renderer` owns LPCM/AAC/Opus dispatch, native libopus versus SDK capability selection, SDK codec-specific bytes, the input pump (10 ms dequeue / 100 ms audio budget), output draining and reusable PCM storage. JNI drives the SDK decoder; Kotlin creates/configures/closes its MediaCodec, presents diagnostics and executes hardware writes. Release each codec output before the synchronous PCM callback, including on copy failure; release exceptions retain Java finally precedence. Never keep a mutable Rust renderer borrow across a host callback: it reenters PCM processing. Direct PCM views cannot outlive that callback; the worker closes their owner after processing returns. Keep AudioTrack/AAudio, focus, route and head-unit calibration behavior.
- Rust `protocols::rtsp` owns control request framing and response encoding behind `RtspMessage`, plus each `RtspInput` reader's encrypted and plaintext residue; only complete messages cross JNI, and the reader borrows the existing cipher under its close monitor. Kotlin retains socket I/O and reader teardown; its private `jni` constructs existing DTOs with bounded local references and UTF-16 strings. Keep the DTO constructor R8 rules, US_ASCII behavior, ProtocolException and receive limits. Rust `protocols::bplist` owns binary plist layout, types and decoding budgets behind `BplistCodec`; its private `jni` maps Java collections/scalars and delegates malformed UTF-16 replacement to the platform charset. Encoding has a shared native/fallback depth limit of 128; decoding retains its 32-level and work/payload limits. Rust `protocols::control_cipher` owns control/event framing, AEAD keys and independent wrapping counters. `ControlCipher` serializes operations and close; `AirPlaySession` closes both owners and rejects late installation. Close the event socket before waiting for its write lock. Keep the Decrypted DTO R8 constructor rule. Rust `iap2_body` owns CSM parameter framing and builder schema rules (type, unknown/repeated/required fields); `iap2_wire` owns scalars, list/terminator layout and typed field sizes. Kotlin retains immutable DTOs, descriptive schema metadata, its builder/reader API and platform UTF-8 conversion; schema errors carry input indexes so UTF-16 field names remain intact. `iap2_csm` owns bounded outer framing, resynchronization and link splitting; `iap2_link` owns synchronization, sequence/ACK/window state, retransmission, bounded queues and timers. These protocol facades require native; CSM/link serialize use with close and the link pump owns its engine with `use`. Old Kotlin algorithms are test-only.
- Rust `protocols::pair_verify` owns the complete M1/M2/M3/M4 handshake, ephemeral/shared/encryption keys, verification result and control keys. `PairVerify` serializes all handle use and close; `AirPlaySession` closes it after transport teardown. Kotlin supplies the live PairingStore lookup and platform UTF-8 conversion. Keep the lookup callback, PairingStore class name and ControlKeys constructor R8 rules. Preserve partial M1 commits, prior verified keys across new/failed handshakes, raw transcripts with first-32-byte crypto keys, and BC 1.79's canonical/low-order Ed25519 rejection boundary. Rust `protocols::pair_setup` owns the full SRP/M1–M6 exchange and proof/signature state. Kotlin retains platform PairingStore callbacks, identity storage and JCA hardware-key actions; Rust owns crypto primitives and MFi DER/raw conversion. Preserve save-before-sign ordering and close/reentry behavior. `num-bigint` modular exponentiation remains variable-time, matching the former BigInteger boundary; do not describe it as constant-time. BC is an independent test oracle, not a production provider.
- Rust `session::wireless_state` defines the opaque value token, queries and transitions for `WirelessRunState`; `session::wireless_recovery` owns run retry budgets, attempt validity/stage/timeout and failure decisions. Kotlin serializes tokens without decoding or duplicating active state. These are values, not heap handles. Kotlin extracts Java Throwable facts and assembles exceptions, and retains validation order, cancellable waits, watchdog scheduling and platform resource actions. Controller generations belong to Rust `session::controller`. Read validity under the attempt monitor, then call the external current predicate after releasing the getter lock.
- Rust `session::connection_recovery` owns whole-stack recovery actions, both host retry counters, backoff and reset rules. Host budgets survive controller/run replacement and remain separate from wireless run-local recovery. Consume both applicable counters when scheduling, including startup/tunnel retries in the whole-stack count; cancellation does not refund them. Preserve distinct resets: session active clears only the whole-stack count; the same session remaining valid for 60 seconds after its first frame clears only startup retries; the Retry button clears both; settings reconnect clears only startup retries. Kotlin retains session reference identity, Handler/Runnable scheduling, menu deferral, callback generations and platform actions without mirrored counters. Bluetooth-off and iAP-tunnel failure kinds come from their producers, never from message matching. Wireless Bluetooth-off remains a manual-retry prerequisite; an explicitly retryable radio failure retains the existing wake-on-radio callback. Preserve USB trust / Wi-Fi reset / terminal failure precedence and terminal-failure retention while the menu defers recovery.
  The same Rust recovery owner holds the host's control-progress/loss observation state and decides whether a queued retry has already recovered. Capture an opaque snapshot when scheduling; skip rebuilding only after a newer RunningControl/RunningWireless report with no subsequent loss. Session active does not substitute for those reports or reset this state. Preserve wrapping counters, host lifetime, loss recording before duplicate-pending guards, and reporter updates before menu/background handling. Kotlin retains Handler cleanup order and generation checks, including clearing pending fields before rejecting a stale timer.
  Menu failure retention and exit recovery selection are pure Rust decisions, without a second native menu state. Kotlin owns the complete deferred failure, pending-event flag, settings validation/save/rollback, menu visibility and Handler. Retain the first failure with requiresUserAction, not every STARTUP_STOP; decide whether to stop from the incoming failure independently. Preserve exit precedence: replay a startup/manual failure on cancel; replay Wi-Fi reset on cancel or when saving into wireless; defer during teardown; rebuild when requested with a controller; otherwise maybe-start. Replaying a failure remains subject to existing deduplication and guards, with no fallback to rebuilding if they reject it. Direct rebuilds do not consume a new retry budget.
  Rust also owns the host-lifetime retained-handshake marker and its transitions. This marker records an explicit decision to keep a pending handshake after StartSession, not Activity visibility. Preserve leave-condition short circuits and the asymmetry that keeping does not require owner/not-shutdown while actual cancellation does. A retained Failed is consumed and clears the marker before Kotlin conditionally stops; it never falls through to menu or ordinary retry handling. onStart and accepted current-generation session-active clear the marker; onStop, no-op navigation and cancellation itself do not. Other error channels are not implicitly Failed events. Keep owner/controller/sink/listener references, Handler, actual stop/adoption and all original generation gates in Kotlin. A new host does not inherit the old host's marker from the background resource snapshot.
  The recovery owner also keeps three distinct host-lifetime failure states: stopped retries, the last startup-failure generation, and an optional USB-pairing-stopped generation. Do not collapse them into one terminal state. Retry and settings reconnect resume retries without clearing either generation; USB wireless fallback also clears the USB marker but retains startup deduplication. Session active does not resume stopped retries. Preserve the initial startup generation -1 and the distinction between an absent USB marker and every Int generation. Filter USB-stopped reports before any status side effects; mark startup failures only at the original branch, before retry guards. Kotlin retains the current generation, UI updates, callback order and Handler work; no mirrored flags or generations.
  USB takeover selection, host reenumeration state, relative 2/10-second waits and fallback action decisions also belong to this recovery owner. Shared usbTakeover remains a Kotlin resource-publication fact, separate from host-lifetime reenumeration. Kotlin retains persistence/USB enumeration, Handler, menu transactions and actual rebuild/prerequisite requests. Preserve short circuits before device enumeration and the any-Apple-device presence check. Attach cancels pending fallback even when takeover is rejected, without clearing reenumeration; WaitingForReenumeration schedules 10 seconds, RunningControl clears/cancels, Failed clears/schedules 2 seconds, and other statuses do not imply those transitions. Repeated scheduling restarts the relative delay. Publish takeover before cancelling menu edits, then read the resulting controller state. Fallback clears takeover/reenumeration before reading saved wireless and clearing recovery state; menu deferral must not overwrite unsaved settings. Preserve retry counts/startup deduplication and the absence of new owner/generation gates.

Kotlin serializes opaque GC value tokens and executes SDK/I/O/clock/cancellation/callback actions. StartService rejections carry a structured reason code (invalid pair record / invalid host id) from Rust, so the platform never classifies the CarKit retry by message text. - Rust `media::video::{pacing, flow, selection}` own input/output timing, reference chains, decoder queues/backlog, byte conversion, codec configuration and degradation. Production video requires the Rust `vpipe` NDK loop (API 28+); initialization failure is explicit, with no Java playback loop. The Kotlin worker carries only the simple `VideoControlMailbox` (FIFO, interruptible wait, close wake, shutdown drain); no frame, budget or chain-discard JNI calls remain on the production control path, and the old Java frame queue exists only as the host pipe's test double. Kotlin retains configuration/Surface requests, capability enumeration, hardware availability probes and SDK resource guards, not duplicate policy state. Keep codec retries, software fallback and vendor parameter degradation. Host SDK pipe replay is test-only and distinct from real Android receiver/FD acceptance. - Rust `protocols::timing` owns request/reply timing, peer correlation, sample selection and clock filtering; Kotlin owns sockets and clock reads. Preserve sample windows, signed/wrapping arithmetic and rounding calibration. Rust `media::video::{annexb, codec}` own screen timestamp/NAL/config layout; `ScreenStream` requires native framing/decryption and keeps platform sockets/callbacks. JNI startup failure releases its descriptor rather than selecting a Kotlin receiver.
- Rust `session::control_deadline` owns the wired Iap2ControlDeadline authentication window, unlimited mode, rounding and bounded polls. Kotlin passes clocks and executes existing wired I/O. Its opaque token has zero or two Long values, interpreted only by the selected core; no heap handle is allocated. Preserve Kotlin wrapping arithmetic, query snapshots before reentrant clock calls and the absence of clock reads after unlimited authentication. Wireless deadlines and watchdog scheduling are separate owners.
- Rust `media::audio::scheduler` owns output accounting, playback/prebuffer state, the granted-capacity start threshold, chunk limits, write-result actions, rebuffer and tail deadlines, buffer calibration and navigation-route decisions. Its facade stays on the renderer worker, allocated lazily, reset in place and closed by worker release. Kotlin executes clock reads and actual play/pause/write/focus/route actions, reporting successful actions back to the core. Renderer compressed packets always use Rust; old Kotlin queue/recovery algorithms are test-only. Rust `media::video::selection` chooses codecs and retry/probe plans; Kotlin reports codec facts, preserves platform Char folding, executes callbacks/create/sleep, and commits retry state after the retry callback. Hardware/SDK capability fallbacks remain platform behavior.
- Rust `media::audio::{capture, uplink}` own microphone frame residue, capture clock, per-frame echo leases, PCM sample statistics/report windows, encoding, RTP/ChaCha counters and the UDP socket. Speex C converts PCM16LE, cancels echo and writes back in the native frame; SpeexDSP is statically linked into `libdiplay_media` beside libopus. Opus capability probes the actual native encoder. `packetizer` supplies capture/clock/MTU calibration and the wire facade, reusing `uplink::seal`. Preserve Int/Long wrapping, 48/24/16 kHz clock priority, 20/10/5 ms MTU calibration, 30 ms echo lead, 250 ms tail and -40/-15 dB suppression. Kotlin retains AudioRecord, SDK timestamp/capability facts, platform effects, start/stop/restart/cancel actions and diagnostic text. A per-id opaque `NativeMicrophone.uplinkConfig` handoff lets Rust own microphone effective-configuration compatibility and the successful-start commit: an identical committed configuration reuses the running sender, any change (port, key or format) replaces it, and the config is committed only after the new sender actually started; Kotlin executes the recorder and platform resources. An identical-key replacement snapshots and resumes the previous sender's ChaCha nonce so nonce space is never reused; a different key starts fresh. Independent packetizer/Concentus references stay test-only.

An unhighlighted lane may still derive its direction from the raw highlight angle when its angles are empty. Other vehicle conversions require actual production callers before adding new adapters.

Wired USB results belong to their diagnostic run. Reject and release stale Connected results, transfer a pipe exactly once to the mux factory, and order mux publication with close/run replacement under the existing resource monitor. Do not close resources or perform I/O under that monitor. A run's finally block terminates only its locally owned startup watchdog, never a replacement run's watchdog.

Rust `vehicle::wheel_keys` owns WheelKeyPresses disposition/commit rules and WheelSiriKey timing state. Each consumer retains independent opaque values; Kotlin owns the Any-key map with its existing equality, null-key handling and callback execution. Keep absent, recorded PASS and recorded consumption distinct. Remove on UP before querying its disposition; call decide only for an unrecorded first DOWN and commit only after it returns normally, preserving its original Action and reentrant outer-write order. No global key registry, lossy hash identity, timeout or implicit session reset. Single/double Siri calls share one nullable timestamp per instance: rejected single presses refresh it, confirmed doubles clear it, 400 ms single and inclusive 180 ms/configured maximum double boundaries preserve wrapping Long subtraction. Invalid maximum intervals throw before state mutation. Kotlin retains time reads, KeyEvent/settings/session references and Handler; Host/service pending decisions, the 1500 ms release window and VoiceKeyPair remain outside this batch.

CarPlayMediaEngine feedback and session-close cleanup must stay scoped to the requesting/closing AirPlaySession identity. Ordinary-audio metadata, pending microphone configurations and packet captures may coexist for multiple sessions in the same engine. Closing one session removes/closes only its own entries; an older session must not stop a microphone id still registered by another session. Keep engine-wide buffered-output retirement barriers, resource locks and platform cleanup ordering; this isolation does not make each session the exclusive owner of shared outputs.

Buffered-audio SETUP validation and its reply layout belong to protocols::airplay::setup; NativeAirPlayProtocol translates the native result once into a named plan. Preserve shk byte-array/length checks, native audio-format selection, optional ct/spf and Java Number longValue/intValue semantics, short-circuit rejection and the type/dataPort/audioBufferSize Int field order. Buffered control method/field interpretation belongs to the existing media::audio::buffered owner, alongside its anchor/state/reply rules. Preserve rtpTime.longValue then rate.doubleValue reads even for unknown/GETANCHOR methods, numeric-only flushUntilTS and original exception identities. Kotlin supplies a raw Long timestamp plus its presence; the buffered JNI owns U32 normalization, keeping missing values distinct from all negative timestamps. Only accepted SETRATE actions read the session NTP clock. Kotlin retains stream lookup, peer/socket facts, creation/binding, locks, cleanup callbacks and platform execution. Native direct media delivery remains with its existing owner.

Instrument content keeps two independent Rust lifetimes: session::controller::dashboard retains accepted cross-session selection, pause/visibility and route epoch; session::airplay::cluster_content retains requested/delivered/shown content and plans/commits for one session's streams. Protocol command bytes and negotiated stream generations stay with their existing owners. Kotlin keeps command/write locks, executor work, actual sends and platform session/route identities. Publish opaque content snapshots with routing identity atomically; route queries never wait for network writes. Commit showUI and keyframe outcomes separately: partial or late successful sends may invalidate delivered content, while failed selection never overwrites the Controller's accepted choice. Preserve paused selection, replay, UTF-16 values, wrapping route counters and all teardown clear paths without inventing an extra negotiation generation.

The buffered shared-output coordinator has engine lifetime, separate from each BufferedAudio stream. Rust owns idle/installing/retirement-only phases, candidate cancellation, retired eligibility and installation/barrier decisions inside the existing audio owner. Kotlin keeps actual owner/transition/stream references, the original ownership lock, WeakHashMap identity entries containing opaque eligibility values, and close/cleanup-complete facts. Never replace weak eligibility with an accumulating Rust session-ID set. Preserve detach-before-close, callbacks outside the ownership lock, cancellation without early barrier release, and normal-close versus completed-cleanup as distinct facts. Cross-session replacement retires the old eligibility at begin even if the candidate is later cancelled; ordinary TEARDOWN does not retire the session. Only the matching transition can commit or release its barrier. Ordinary audio and cluster resource identities remain independent of this buffered coordinator.

Rust `media::output_lease` owns the non-buffered stream identity and output-sharing leases: each accepted audio, microphone and screen output registers a lease keyed by (engine epoch, kind, stream type, audioType) plus the holder session, and only the last release of an output identity may stop it. Kotlin acquires on each accepted stream/microphone/screen and releases at the matching removal (teardown, session close, peer EOF, replacement), using the returned last-release fact to decide whether to stop the sink output; it keeps the actual Closeable, AudioMeta, capture, CAS outcomes and resource identities. `audio::scheduler` still decides duck notification. An old teardown/close/EOF must not stop a still-registered replacement id/type; preserve the final owner's cleanup and empty-owner repeated unduck, and an unrelated old unduck cannot clear the current prompt. Teardown and session close detach and close a source stream before releasing its lease, so a final flush lands on a live renderer; only the last holder stops the shared output. A screen or data teardown never releases an audio/microphone lease, and a same-session re-SETUP stops the shared output only when it is the last holder. The lease decides who may stop an output; delivery admission is separate: when a new route takes over the same AudioStreamId, the previous audio route is permanently retired (its later packets are dropped in Rust, never handed to the switchboard) so a replaced session's still-open stream cannot feed the new output, while a renderer-failure detach stays recoverable and still falls back to the sink. Audio route disconnect still permits same-stream renderer recovery, and microphone sender/config replacement remains a separate boundary.

## Adding or moving a setting

The Settings screen is grouped by driver goal, not by implementation.
`SettingsCategory`, `SettingsSection` and `SettingsInformationArchitecture` in
`common/src/main/java/com/shihab/diplay/SettingsInformationArchitecture.kt` define the groups.
`SettingsLayoutPolicyTest` fails when a section has no category or has more than one.

### Choose the category

Ask which goal the driver has when they look for the setting. Use the first row that fits.

| Category | Put a setting here when it controls… | Examples |
| --- | --- | --- |
| Connection | how the iPhone connects and how DiPlay starts | connection setup, connect on open, start with the car, USB permissions, car hotspot automation, iPhone choice, Android permissions |
| Display | how CarPlay looks on the head-unit screen | day/night mode, picture, size, resolution, frame rate, dock, system bars, multi-window resolution |
| Audio | what the driver hears | media and navigation streams, music buffer |
| Navigation | location and turn-by-turn guidance | location to iPhone, head-unit HUD and cluster guidance |
| Vehicle | how CarPlay fits this car and its driver | driving side, wheel keys (Siri, joystick and map zoom), car button, gestures that conflict with the head unit |
| Diagnostics | troubleshooting evidence | diagnostic reports |
| Advanced | experimental, firmware-specific or risky behavior | dashboard map, split screen, screen rotation, side panel, HEVC video, audio focus, audio channel mapping, buffered music, vehicle data |
| Overview | nothing new | see "Overview" below |

A setting goes to Advanced when it is experimental, depends on specific firmware, or is an opt-in that can break sound, video or the connection on some head units.
A control that fixes a common problem and is safe at its default (for example the audio stream choice) stays in its category.
Exception: a gated control that only its own audience sees, and that completes an everyday goal, stays in that goal's category.
Example: auto car hotspot depends on vehicle permissions and appears only for car-hotspot users, so it is in Connection.

Mark an experimental setting or card with the title suffix ` (experimental)`, never `· experimental`, a dash, or an `Experimental …` prefix.
Each locale MUST use its existing form: `(تجريبي)`, `(experimental)`, `(sperimentale)`, `(экспериментально)`, `(експериментально)`, `（实验性）`, `（實驗性）`, `（実験的機能）`.

### Add the code

1. To extend an existing card, add the control inside the `filteredSection(...)` block of a card in the correct category.
2. For a new card, add a `SettingsSection` entry and map it to exactly one category in `SettingsInformationArchitecture.sectionsByCategory`.
3. Build the new card with `filteredSection(content, SettingsSection.X, …)` inside `allSettingsSections()`.
   A plain `section(...)` call there MUST NOT be used: it renders on every category page.
4. A setting MUST NOT appear in two categories.
   Overview quick settings are the only duplicates. They MUST use the same persistence as the full control. Overview SHOULD NOT have more than four quick settings.
   A header shortcut MAY duplicate a Display setting when it uses the same persistence.
5. If the change reconnects CarPlay or applies at the next connection, the description MUST say so.
   A setting that only takes effect at the next connection MUST call `markReconnectNeeded()` after it saves.
   This shows the "Reconnect now" bar. It MUST NOT drop a running session without the driver's consent.
   Reconnect at once (`reconnectIfRunning()`) only after a dialog button that says "Apply and reconnect", or when the description says that the change reconnects CarPlay.
6. Add each new string to `common/src/main/res/values/` and to every `values-xx` locale folder.
   New Settings copy SHOULD use the `settings_` prefix. `SettingsTranslationsTest` fails when a `settings_*` string has no translation.
7. A control that opens a choice uses `button()` with the text `"Title · Value"`.
   That form renders as a setting row with the value and a chevron, and Search indexes the title.
8. When you move a control between categories, update `AdaptiveSettingsUiTest.settingsLiveWhereDriversLookForThem`.

### Overview

Overview holds the connection status, links to the categories, quick settings, About and Language.
Do not add a new setting to Overview. Add it to its category. Then promote it to quick settings only if drivers change it often.

## Settings layout

Spacing, size and shape in the Settings screen MUST come from one place.

1. A gap between blocks MUST use a named dp constant, such as `SETTINGS_BLOCK_GAP_DP`.
   A new literal gap value MUST NOT be added.
2. A size MUST NOT be a pixel constant (`*_PX`). Use dp, and clamp to the available window width.
   Test menus and panels on the current head unit at 1920×1080 pixels.
3. Controls in one row MUST have the same height.
   Corner radius MUST follow the control height. A new button MUST NOT set its own radius.
4. Every `SettingsCategory` except Overview MUST have a link on Overview.
   `AdaptiveSettingsUiTest.overviewLinksToEveryOtherCategory` checks this.
5. A layout change MUST include a screenshot at the current head unit size: 1920×1080 pixels,
   landscape, normal font scale. Do not add other screen sizes, portrait, large-font or RTL
   screenshot variants. Keep protocol and instrument-display dimension tests for their own formats.

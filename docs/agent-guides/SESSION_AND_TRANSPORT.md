# Session and transport ownership

Read for connection lifecycle, recovery, Bluetooth/hotspot, USB/VPN, wired handshakes or dashboard content. For wire formats also read [Protocols](PROTOCOLS.md); for stream lifetimes read [Media](MEDIA.md); for host views read [UI and settings](UI_AND_SETTINGS.md#host-components).

These rules are part of [AGENTS.md](../../AGENTS.md). Apply its global ownership and validation rules as well. Paths in code spans are relative to the repository root.

## Controller and wireless resources

- `CarPlayController` executes shared-service and wired teardown actions; its private `WirelessRun` retains one wireless generation's platform resources, callbacks and cleanup. Rust `session::{controller, wireless_state, wireless_recovery, watchdog}` own generations, lifecycle/handoff, retry budgets, deadlines and teardown decisions. Wi-Fi scan suppression stays with the controller across runs. `WirelessBluetoothConnection` selects and validates Bluetooth SDK targets and connects RFCOMM using the caller's cancellation predicate. `CarPlayStatus` holds the status contract. Its debug-log line for each status lives next to it (`debugLogMessage`), and `OrchestrationText` holds the text helpers shared across the package.

- Rust `session::bt_profile_guard` owns the Bluetooth profile-guard decisions: yield mode/delay/skip, paused-by-us, restore phase, startup-recovery gate, passive boot-radio observation and adapter-ready rejection. Kotlin `CarBluetoothProfileGuard` keeps every `BluetoothAdapter`/profile-proxy verb, broadcast receiver, retry thread and the persisted restore journal; `testCoreShadows` carries an independent Kotlin reference so Robolectric tests do not need the native core. `BluetoothAdapterRestore.awaitOn` stays a platform wait loop.

- Rust `session::wireless_state` defines the opaque value token, queries and transitions for `WirelessRunState`; `session::wireless_recovery` owns run retry budgets, attempt validity/stage/timeout and failure decisions. Kotlin serializes tokens without decoding or duplicating active state. These are values, not heap handles. Kotlin extracts Java Throwable facts and assembles exceptions, and retains validation order, cancellable waits, watchdog scheduling and platform resource actions. Controller generations belong to Rust `session::controller`. Read validity under the attempt monitor, then call the external current predicate after releasing the getter lock.

## Host recovery

- Rust `session::connection_recovery` owns whole-stack recovery actions, both host retry counters, backoff and reset rules. Host budgets survive controller/run replacement and remain separate from wireless run-local recovery. Consume both applicable counters when scheduling, including startup/tunnel retries in the whole-stack count; cancellation does not refund them. Preserve distinct resets: session active clears only the whole-stack count; the same session remaining valid for 60 seconds after its first frame clears only startup retries; the Retry button clears both; settings reconnect clears only startup retries. Kotlin retains session reference identity, Handler/Runnable scheduling, menu deferral, callback generations and platform actions without mirrored counters. Bluetooth-off and iAP-tunnel failure kinds come from their producers, never from message matching. Wireless Bluetooth-off remains a manual-retry prerequisite; an explicitly retryable radio failure retains the existing wake-on-radio callback. Preserve USB trust / Wi-Fi reset / terminal failure precedence and terminal-failure retention while the menu defers recovery.
  The same Rust recovery owner holds the host's control-progress/loss observation state and decides whether a queued retry has already recovered. Capture an opaque snapshot when scheduling; skip rebuilding only after a newer RunningControl/RunningWireless report with no subsequent loss. Session active does not substitute for those reports or reset this state. Preserve wrapping counters, host lifetime, loss recording before duplicate-pending guards, and reporter updates before menu/background handling. Kotlin retains Handler cleanup order and generation checks, including clearing pending fields before rejecting a stale timer.
  Menu failure retention and exit recovery selection are pure Rust decisions, without a second native menu state. Kotlin owns the complete deferred failure, pending-event flag, settings validation/save/rollback, menu visibility and Handler. Retain the first failure with requiresUserAction, not every STARTUP_STOP; decide whether to stop from the incoming failure independently. Preserve exit precedence: replay a startup/manual failure on cancel; replay Wi-Fi reset on cancel or when saving into wireless; defer during teardown; rebuild when requested with a controller; otherwise maybe-start. Replaying a failure remains subject to existing deduplication and guards, with no fallback to rebuilding if they reject it. Direct rebuilds do not consume a new retry budget.
  Rust also owns the host-lifetime retained-handshake marker and its transitions. This marker records an explicit decision to keep a pending handshake after StartSession, not Activity visibility. Preserve leave-condition short circuits and the asymmetry that keeping does not require owner/not-shutdown while actual cancellation does. A retained Failed is consumed and clears the marker before Kotlin conditionally stops; it never falls through to menu or ordinary retry handling. onStart and accepted current-generation session-active clear the marker; onStop, no-op navigation and cancellation itself do not. Other error channels are not implicitly Failed events. Keep owner/controller/sink/listener references, Handler, actual stop/adoption and all original generation gates in Kotlin. A new host does not inherit the old host's marker from the background resource snapshot.
  The recovery owner also keeps three distinct host-lifetime failure states: stopped retries, the last startup-failure generation, and an optional USB-pairing-stopped generation. Do not collapse them into one terminal state. Retry and settings reconnect resume retries without clearing either generation; USB wireless fallback also clears the USB marker but retains startup deduplication. Session active does not resume stopped retries. Preserve the initial startup generation -1 and the distinction between an absent USB marker and every Int generation. Filter USB-stopped reports before any status side effects; mark startup failures only at the original branch, before retry guards. Kotlin retains the current generation, UI updates, callback order and Handler work; no mirrored flags or generations.
  USB takeover selection, host reenumeration state, relative 2/10-second waits and fallback action decisions also belong to this recovery owner. Shared usbTakeover remains a Kotlin resource-publication fact, separate from host-lifetime reenumeration. Kotlin retains persistence/USB enumeration, Handler, menu transactions and actual rebuild/prerequisite requests. Preserve short circuits before device enumeration and the any-Apple-device presence check. Attach cancels pending fallback even when takeover is rejected, without clearing reenumeration; WaitingForReenumeration schedules 10 seconds, RunningControl clears/cancels, Failed clears/schedules 2 seconds, and other statuses do not imply those transitions. Repeated scheduling restarts the relative delay. Publish takeover before cancelling menu edits, then read the resulting controller state. Fallback clears takeover/reenumeration before reading saved wireless and clearing recovery state; menu deferral must not overwrite unsaved settings. Preserve retry counts/startup deduplication and the absence of new owner/generation gates.

## Handshakes, wired transport and deadlines

- Rust `session::{controller, watchdog, airplay, iap2_handshake}` own controller/run/VPN generations and leases, lifecycle/teardown decisions, watchdog deadlines, RTSP negotiation/stream claims, event-channel command dispatch, per-session remote-control stream id allocation and identification/MFi/wired/wireless handshake actions, retries and counters. Kotlin serializes opaque GC value tokens and executes SDK/I/O/clock/cancellation/callback actions. Keep existing deadlines, wrapping, callback order, late-result disposal and SDK work outside core/resource locks. `transport::usbmux` owns framing, mux/TCP sequence/window/queues and send-success commits; `transport::lockdown` owns XML/plist framing and Pair/StartSession/StartService flows. The pairing and CarKit clients consume named actions decoded in one place (`LockdownJniEffects`): their loops read typed fields only, never JNI action indices, metadata casts or raw action numbers, and an unknown or malformed layout fails as a contract error before any I/O starts. StartService rejections carry a structured reason code (invalid pair record / invalid host id) from Rust, so the platform never classifies the CarKit retry by message text. Kotlin retains I/O, waits, exception references and PKIX identity/storage adapters. Simple SDK thread handoff mailboxes remain platform I/O adapters. Rust `session::wired_stack` owns the wired saved-pair-record/CarKit retry classification, the control-loop terminal outcome, the bring-up order (`advance(action, approved)` emits the next USBMUX/pair/CSM/VPN/endpoint/control stage and its abort branch), and the teardown release plan (`teardownPlan(phase, facts)` returns the ordered release actions and the NCM-close vs VPN-detach branch for the exception/finally paths). Kotlin executes each stage's I/O, reports the gate fact, and calls the existing close/detach statements verbatim.

- Rust `session::control_deadline` owns the wired Iap2ControlDeadline authentication window, unlimited mode, rounding and bounded polls. Kotlin passes clocks and executes existing wired I/O. Its opaque token has zero or two Long values, interpreted only by the selected core; no heap handle is allocated. Preserve Kotlin wrapping arithmetic, query snapshots before reentrant clock calls and the absence of clock reads after unlimited authentication. Wireless deadlines and watchdog scheduling are separate owners.

Wired USB results belong to their diagnostic run. Reject and release stale Connected results, transfer a pipe exactly once to the mux factory, and order mux publication with close/run replacement under the existing resource monitor. Do not close resources or perform I/O under that monitor. A run's finally block terminates only its locally owned startup watchdog, never a replacement run's watchdog.

## Network address and hotspot startup

- Rust `session::network_address` owns hotspot address selection/alternate ordering, scoped IPv6 readiness/filtering, bounded preferred-family waits and the evidence gate for persisting a family flip; Bonjour endpoint selection has its distinct IPv4/link-local/global/fallback order in this same owner. Kotlin supplies InetAddress capability facts and retains interface scans, cancellation, waits, logs and preference storage. Ordinary hotspot selection still accepts unscoped link-local IPv6; preferred-family recovery requires scoped link-local before ending its wait.

- Rust `session::hotspot_recovery` owns stable-sample confirmation, first-sample fast confirmation with change fallback, hotspot readiness deadlines/polls, radio-return wait budgets and process-wide radio outage expiry. Kotlin retains Android AP/interface identification and identity comparisons, clock/cancellation reads and SDK polling. Preserve callback/clock order, the 2/3-sample thresholds and 250/500 ms polls.

- Rust `session::p2p_startup` owns remembered-frequency validation, aligned/band/manual channel plans, bounded BUSY retry and compatibility fallback decisions. Kotlin retains WifiP2pManager operations, platform prerequisites/interlocks and original exception identities; uncertain timeouts cannot trigger another create request.

## Dashboard content lifetimes

Instrument content keeps two independent Rust lifetimes: session::controller::dashboard retains accepted cross-session selection, pause/visibility and route epoch; session::airplay::cluster_content retains requested/delivered/shown content and plans/commits for one session's streams. Protocol command bytes and negotiated stream generations stay with their existing owners. Kotlin keeps command/write locks, executor work, actual sends and platform session/route identities. Publish opaque content snapshots with routing identity atomically; route queries never wait for network writes. Commit showUI and keyframe outcomes separately: partial or late successful sends may invalidate delivered content, while failed selection never overwrites the Controller's accepted choice. Preserve paused selection, replay, UTF-16 values, wrapping route counters and all teardown clear paths without inventing an extra negotiation generation.

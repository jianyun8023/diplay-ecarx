# 媒体流原生解密实测（2026-11-11）

CarPlay 屏幕流的每一帧、音频流的每一个包都要做一次 ChaCha20-Poly1305 认证解密。
本次对比平台 `Cipher`（Conscrypt，`AndroidOpenSSL`）与 `libdiplay_chacha.so`（Rust + ring，
ChaCha20/Poly1305 为 BoringSSL 汇编）。原生库来源、SHA-256 和重建命令见
[NOTICE](../../shared/src/main/jniLibs/NOTICE.md)。

## 为什么慢的不是算法

车机和手机日志里，视频解密平均 430–650 µs/帧，而且几乎与帧大小无关：686 B 的帧 434 µs，
27 KB 的帧约 1 ms。说明主要是每次调用的固定开销，不是按字节计算的部分。

小米 8 上用 `app_process` 微基准复现：

| 3.3 KB 一帧 | 连续调用 | 每 16 ms 一帧（接近实际） |
|---|---:|---:|
| 平台 `Cipher`：`init` + `doFinal` | 30 µs | 450–530 µs |
| 只做 `Cipher.init` | 16 µs | 约 280 µs |
| 平台 `Cipher`，复用密钥与输出数组 | 27 µs | 450 µs |
| Rust + ring，经 JNI | 13 µs | 约 100 µs |
| 空 JNI 调用 | 1 µs | 35 µs |

帧间隔 16 ms 时，CPU 降频、缓存变冷，Java `Cipher` 调用链本身就要约 0.3 ms。
在 Kotlin 里复用数组只能省约 5%；绕开 `Cipher` 才能去掉这部分。

## 小米 8 实际会话 A/B

- 小米 8，SDM845，LineageOS Android 15；屏幕 1920×1080 横屏，另有一块 1920×720 仪表叠加屏。
- 同一 APK（v148 car-test），用开关切换解密实现；每组重启应用、重新连接 iPhone，
  导航（地图移动）+ 音乐播放，取 `StreamReceiveStats` 300 秒窗口。
- 接收线程 CPU 来自本 PR 新增的 `threadCpuMs`（`Debug.threadCpuTimeNanos()`）。

两组负载接近：视频 22.8 + 10.7 fps 对 22.1 + 12.3 fps，音乐流均为 46.8 包/秒。

| 流 | 解密平均 / 最大：平台 → 原生 | 接收线程 CPU / 帧或包：平台 → 原生 |
|---|---|---|
| 主屏视频 | 385 µs / 4.6 ms → 81 µs / 1.9 ms | 934 → 768 µs（−18%） |
| 第二路视频 | 384 µs / 4.8 ms → 96 µs / 1.8 ms | 930 → 682 µs（−27%） |
| 音乐（type 102） | 102 µs / 1.8 ms → 19 µs / 0.5 ms | 228 → 138 µs（−39%） |

接收线程合计约省 11 ms CPU/秒，约为小米 8 一个核心的 1.1%。解密之外，视频接收线程每帧仍有
约 0.7 ms CPU，其中约 35–40% 是内核态（socket 读取）；这部分不受本改动影响。

## 结论与限制

- 解密耗时降为约 1/4–1/5，尾部延迟同步下降；对体感卡顿没有直接证据。
- 这是小米 8（Android 15）数据。820A 车机（Android 9）日志里平台路径的耗时与此相近，
  但原生路径尚未在车上实测。
- 原始日志、APK 和脚本保存在工作区，不在仓库内。
